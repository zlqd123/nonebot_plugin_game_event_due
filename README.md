# nonebot-plugin-game-event-due

二游活动日历：**每天中午拍一次 24 小时窗口快照，把窗口内发生变化的
活动合并成一条推给群**。支持图文混排，数据源是
[SRA 公共 API](https://starrailassistant.top/api/v1/activity/)。

> 由 AstrBot / Koishi 同名插件重写而来，见 [来源](#来源)。本分支是 NoneBot2 实现。

## 它做什么

检查点固定为**当天 12:00:01**，前后各取 24 小时，把落进窗口的活动按四组
切分，顺序固定，合并成**一条**消息发给群：

```
🎮 明日方舟：终末地
▎已开始（4）
· 「归野」叙事活动　11-05 12:00~11-26 05:59
· 「星河共我」签到活动　11-05 12:00~11-26 05:59
· 「危机合约 浸蓝测试作战」挑战活动　11-05 12:00~11-26 05:59
· 「狂热赛季」（战争回响）　11-05 12:00~11-26 05:59
▎已结束（6）
· 「卡莉的芳菲童话」拍照活动　11-05 04:00
· 「丰碑留名·魇林」限时挑战　11-05 04:00
· 「危机筹备」限时活动　11-05 04:00
· 「万物有灵」签到活动　11-05 11:59
· 「异想赛季」（战争回响）　11-05 11:59
· 「墨分诸彩」引入活动　11-05 12:00
```

四组都可能为空，空组不显示；四组全空就**一个字都不发**。所以平时很安静，
只在活动交接日出现一条。

窗口（C = 检查点，W = `window_hours` 小时，默认 24）：

| 分组 | 判定 |
| --- | --- |
| 已开始 | `C-W <= start < C` |
| 即将开始 | `C <= start <= C+W` |
| 即将结束 | `C <= end <= C+W` |
| 已结束 | `C-W <= end < C` |

一个活动只归一组，按上表顺序取第一个命中的（防止同一活动出现在两组里）。
开始组写完整时段 `开始~结束`，结束组只写结束时刻；每行都只到时间，不带
方向动词。

## 特性

- 支持 18 款游戏：明日方舟、终末地、星铁、原神、绝区零、鸣潮、异环、蔚蓝档案三服、
  星塔旅人、无限暖暖、少女前线2、战双帕弥什、卡厄斯梦境、棕色尘埃2、NIKKE、火影忍者
- **每群每天最多一条**，多个游戏、四个分组全部合并
- 每行只有「标题 + 时间」，标题行不带窗口字样，行尾不带「开始/结束」
- 检查点钉死在 **12:00:01**，整点时间戳归属无歧义；窗口每天移动，天然不重复
- 兼容 OneBot v11 与 QQ 官方 Bot（QQ 适配器为可选依赖，不硬 import）
- 插件自身不暴露任何群内指令

## 安装

```bash
# 推荐：带定时任务与缓存目录管理
pip install nonebot-plugin-game-event-due[scheduler,localstore]
```

在 `pyproject.toml` 里加载：

```toml
[tool.nonebot]
plugins = ["nonebot_plugin_game_event_due"]
```

或直接把目录丢进 `extra_plugins/`（`plugin_dirs = ["extra_plugins"]` 会自动发现）。
缺 `nonebot_plugin_apscheduler` 时插件仍能加载，只是不会有任何定时推送。

## 指令

**没有。** 订阅与推送范围完全由管理员在配置文件里决定，群成员无法改动。
历史指令（`/活动订阅`、`/活动查询`、`/活动阈值` …）的代码完整保留在
`events/commands.py` 的注释块里，需要恢复时解开对应片段即可。

## 配置

环境变量前缀 `GAME_EVENT_DUE_`，嵌套用双下划线，例如
`GAME_EVENT_DUE_DAILY_PUSH__HOUR=12`。

### 检查节奏与窗口

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `daily_push.hour` / `minute` | `12` / `0` | **检查时刻**（东八区）。一天只跑这一轮 |
| `check_second` | `1` | 检查点秒数，即 **12:00:01**。别改成 0 |
| `window_hours` | `24` | 窗口宽度（小时），检查点前后各取这么长 |
| `quiet_hours` | `"23-8"` | 仅旧档位路径使用；窗口快照**不看静默时段**，每天必发 |

**为什么是 12:00:01**：上游 SRA 的时间戳都是整点。差这一秒，归属就毫无歧义
——`12:00:00` **开始**的活动归「已开始」，`12:00:00` **结束**的归「已结束」。
严格按 C 判定，**不加整点例外**。真正执行往往比 cron 晚几百毫秒，代码会把
检查点归一到配置时刻，不让亚秒抖动影响归属。

`daily_push.enabled` 只管「全量摘要」那条，**不影响检查时刻**——即使关掉摘要，
12:00:01 的检查照常进行。窗口快照不走档位状态机，`deadline_push.thresholds`
/ `start_push.thresholds` 对它无效；它们只影响「每日全量摘要」等旧路径。

### 订阅

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `preset_subscriptions` | `""` | 唯一的订阅入口，格式见下 |
| `notify_new_activity` | `true` | 新活动出现时是否提醒（旧路径） |
| `notify_on_subscribe` | `true` | 下发订阅后是否立刻推一次概览 |

### 数据源与缓存

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `sra_api_base` | SRA 地址 | 数据源基址 |
| `request_timeout` | `20` | 请求超时（秒） |
| `proxy` | `""` | 代理，留空不走代理 |
| `cache_dir` | `""` | 缓存目录；留空用 localstore，再退化为包内 `.cache` |
| `fetch_interval_hours` | `8` | 手动刷新时的缓存最大年龄（天级检查会强制取数，不受它限制） |
| `refresh_on_start` | `true` | 启动时预热一次缓存 |

### 消息格式

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `window_hours` | `24` | 窗口宽度（小时），前后各取这么长 |
| `check_second` | `1` | 检查点秒数，12:00:01 |
| `single_message_per_game` | `true` | 合并成一条（关掉会按游戏分别发送） |
| `activity_separator` | `━━━━…` | 活动之间的分隔线；想更紧凑可设为空 |
| `urgency_marker` | `true` | 紧急度色块 |
| `sort_by_urgency` | `true` | 同一分组内按时间由近到远排序 |
| `insert_cover` | `true` | 有版本主视觉就配一张图，没有就纯文字 |
| `game_aliases` | `""` | 自定义显示名，如 `sr=星铁,ak=舟游` |

## 图文混排

**有图插图，无图文字**——不需要额外开关，取决于数据源给不给得出图。
24 小时提醒和每日全量摘要都带图。

配图来源是 SRA 游戏 JSON 的**根级 `cover`**（版本主视觉）。活动级的
`cover` 绝大多数是同一张图重复挂（实测终末地 14 个活动里 9 个挂同一张），
所以插件只按游戏取一张：根级有就用根级，没有就退而取活动里出现次数最多
的那张，一张都没有就纯文字。

### 两个平台的能力差得很远

| 平台 | 怎么发图 | 结果 |
| --- | --- | --- |
| OneBot v11 | `[CQ:image,file=<url>]` 内联 | 一条消息里真·图文混排，多游戏也只要一条 |
| QQ 官方 Bot | `msg_type=7` 富媒体 | **一条消息只能带一张图**，多游戏按游戏拆成多条 |

QQ 官方这边踩过的坑，记下来免得以后又试一遍：

- markdown（`msg_type=2`）里写 `![alt](url)` **不渲染图片**，实测连外链也不行，
  客户端只会把方括号里的文字当链接显示出来；
- `msg_type=8` 图文卡片（`card.tuwen`）在这个 Bot 上返回
  `404 不支持的调用`（`40011002`）；
- 所以只剩 `msg_type=7`，适配器的 `MessageSegment.file_image()` 会自己完成
  `post_group_upload` 换 `file_info` 再发，不需要手动调上传接口。

因此 QQ 群的实际效果是**一个游戏一条消息**：一张版本主视觉 + 该游戏的
四组窗口清单。两个游戏就是两条，内容各自完整，不重复不刷屏。

实际渲染（2026-11-04 真机数据）：

```
[消息 1] 图片：终末地版本主视觉
         文字：🎮 明日方舟：终末地
               ▎即将结束（6）
               · 「丰碑留名·魇林」限时挑战　11-05 04:00
               · 「卡莉的芳菲童话」拍照活动　11-05 04:00
               ...
               ▎即将开始（4）
               · 「归野」叙事活动　11-05 12:00~11-26 05:59
               ...

[消息 2] 图片：方舟版本主视觉
         文字：🎮 明日方舟
               ...
```

### 降级

任何一步失败都退回纯文字，图片变成可点的「封面：<链接>」，正文照发：

- 图片下载失败 / 超过 8MB / 非图片 → 该条只发文字；
- 适配器没有 `file_image`（比如频道）→ 只发文字；
- 发送富媒体失败 → 该条改用纯文本重发。

绝不因为配图挂了而丢掉整条推送。

想彻底关掉图片：`GAME_EVENT_DUE_INSERT_COVER=false`。

## 预置订阅

```dotenv
GAME_EVENT_DUE_PRESET_SUBSCRIPTIONS=qq:group:0123456789ABCDEF=方舟,终末地@1~1
```

格式 `会话key=游戏列表@结束档位~开始档位`：

| 写法 | 含义 |
| --- | --- |
| `@1` | 只在活动**结束前**不足 1 天时提醒 |
| `~1` | 只在活动**开始前**不足 1 天时提醒 |
| `@1~1` | 两个方向都要（推荐） |
| `@7,3,1~1` | 结束方向 7/3/1 天三个档位 |
| `@~` | 两个方向都关闭 |
| 全省略 | 沿用全局 `deadline_push` / `start_push` |

- `会话key` 形如 `qq:group:<群 openid>` / `onebot:group:<群号>`；
- 游戏支持代号与中文别名（`ak`/`方舟`、`end`/`终末地`、`sr`/`星铁` …）；
- 多条用换行或 `;` 分隔；私聊会话会被跳过并告警；
- 同一份配置**只应用一次**（按内容签名判断），之后重启不会覆盖群里的设置；
  想重新下发，改动 `preset_subscriptions` 这一行内容即可。

新活动出现时不会补推历史活动：首次运行时会把当时在册的活动标记为已知，
避免一次性收到几十条。

## 推送规则

一天只有一轮，检查点 `C = 当天 12:00:01`，窗口 `W = window_hours`（默认 24h）。
四组判定见 [它做什么](#它做什么)，顺序固定「已开始 → 即将开始 → 即将结束 →
已结束」，空组不显示。

| 类型 | 触发条件 |
| --- | --- |
| 已开始 | 过去 W 内开始的活动 |
| 即将开始 | 未来 W 内开始的活动 |
| 即将结束 | 未来 W 内结束的活动 |
| 已结束 | 过去 W 内结束的活动 |

几条边界行为：

- **未来侧闭区间**：恰好 `C+W` 开始/结束算进窗口，多一秒不算。这条必须闭，
  否则「明天 12:00 整」的活动会掉进今天和明天两轮之间的缝隙里。
- **过去侧含下界**：恰好 `C-W` 开始/结束算进窗口。
- **严格 12:00:01、无整点例外**：`12:00:00` 的时间戳一律落在「过去」侧。
- **一个活动只归一组**：同时命中多组时按上表顺序取第一个，不会重复出现。
- **不看静默时段**：12:00 是人工选定的时间，到点就发；`quiet_hours` 只作用于旧的档位路径。
- **不写档位状态**：窗口每天移动，天然不需要「一个活动只播一次」的去重。
  仍用每日推送日期保证「每群每天最多一条」，重启/重跑都不会补发。
- **每群每天最多一条**：多个游戏合并进一条消息；发送失败则不记日期，下一轮重试。
- 每条消息的长度受 QQ 平台限制，超长建议设 `activity_separator` 为空或关掉
  `urgency_marker`。

## 缓存行为

| 场景 | 行为 |
| --- | --- |
| 每天 12:00 检查 | 强制向上游取数 |
| 插件启动 | 缓存仍在磁盘上，立即可用；`refresh_on_start` 决定是否立刻预热 |
| 上游故障 | 回退到磁盘缓存并在日志里标注 |

## 已知限制

- 配图只有**每个游戏一张版本主视觉**，没有活动级独立插画（数据源里就没有）
- 卡池（`pools` 字段）暂不解析
- 不支持多轮补充查询：一天只有一次检查。窗口是 ±24 小时，活动若在两次
  检查之间开始并结束（时长 < 24h 且完全错开检查点），可能只在某一天出现一次
- 上游数据由 SRA 社区人工维护，时间以官方公告为准
